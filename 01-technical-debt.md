Coming from a background of cybersecurity, a couple of the examples of technical debt stand out as familiar, but through a different lens.  Both dead experimental code paths and glue code has an interesting parallel with modern cybersecurity vulnerability management.  Commercial software products contain large numbers of third-party packages and dependencies, many of which are partially used, or potentially not used at all.  Even if an organization maintains a software bill of materials (SBOM), knowing that a package exists is not the same as knowing why it exists, whether it's actually required, or what will break if you remove it.  The same problem is present in a machine learning research project.  Experimental code paths may no longer contribute to the final model, but they remain because nobody still around or actively contributing to the project remembers why the code paths exist or if they can be removed safely.  The practice taught in this course (will be taught) to mitigate this, at least partially, would be tests.  A pytest suite can provide results that removing unused code has not broken the system.  However, religious testing practices do not answer the question of **why** a particular piece of code still exists.

This is where experiment tracking becomes particularly valuable. If an experiment, dependency, or processing step has a documented purpose and its relationship to a particular result is recorded, we have evidence for determining whether it is still necessary.  In that sense, experiment tracking serves a role somewhat analogous to an SBOM: it provides visibility into the components of a system. However, the analogy has limits. An SBOM primarily answers “what is in the software?”, while good experiment tracking can help answer “why is this component here, what experiment depended on it, and what happens if I change it?”

Thus, these practices do not eliminate the CACE problem, but they can make the system's dependencies more visible and make changes less risky.

For a semester-scale research report, I think **dead experimental code paths** are particularly likely to become technical debt. Learning while writing code naturally involves experimentation, so code is often written to test an idea rather than to become part of the final system. Once an experiment has failed or been replaced, however, the code may remain because removing it seems less important than moving on to the next experiment.  Furthermore, there might be a good idea still buried in there.  Let's not **delete** that, I might need it later.

I would prevent this by treating experiments as explicitly tracked and disposable components. Each experiment should have a documented purpose, configuration, results, and conclusion. Once an experimental approach is rejected, I would either remove its code or clearly separate it from the production path and document why it was retained. Automated `pytest` tests would also make it safer to remove old code because they provide evidence that the remaining system still behaves correctly.
